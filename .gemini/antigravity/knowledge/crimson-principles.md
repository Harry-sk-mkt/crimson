# Crimson Principles

이 문서는 `crimson` 마더 프로젝트 산하 모든 도메인(`blog/`, `lead-tracker/`, `meetings/`, `email/`, `context/`)에 공통 적용되는 상위 엔지니어링/작업 원칙입니다.

각 도메인은 자체 `CLAUDE.md`/문서에 더 구체적인 규칙(예: `lead-tracker/CLAUDE.md`의 Staged ETL 구조)을 가질 수 있지만, 이 문서의 원칙과 충돌해서는 안 됩니다. 원칙 자체는 최초 `crimson-lead-tracker` 프로젝트에서 검증된 뒤 이 마더 프로젝트로 승격되었습니다 (승격: 2026-09-21).

## No Assumptions

파일/시트 이름, 컬럼/필드 인덱스, 스키마, 기존 함수·아키텍처를 절대 추측하지 않는다. 모르면 반드시 확인하거나 질문한다.

- 도메인이 다르면 겉보기에 비슷한 개념(예: "리포트", "상태")도 실제 구현이 다를 수 있다 — 다른 도메인의 관례를 그대로 가정해 적용하지 않는다.
- 추측이 필요한 시점에는 작업을 멈추고 질문하는 것이 잘못된 추정으로 작업을 진행하는 것보다 항상 낫다.

## Configuration Centralized

모든 설정값(경로, ID, 임계값, 키 등)은 도메인별로 지정된 단일 설정 지점에만 존재해야 한다. 코드/문서 여러 곳에 흩어진 하드코딩을 금지한다.

- 예: `lead-tracker`는 `CORE_001_Config.js`의 `CONFIG` 객체가 유일한 설정 소스.
- 새 도메인(`meetings/`, `email/`, `context/` 등)에 설정이 필요해지면, 해당 도메인 안에 동일한 원칙으로 단일 설정 지점을 먼저 정의한다.

## TDD (Test-Driven Development)

새 함수를 만들거나 기존 함수를 수정할 때는 반드시 다음을 함께 작성한다:

1. 이 함수/로직이 **왜 필요한지**(WHY)를 상단에 명시.
2. 구현 완료 후 **기대값과 실제값을 비교 확인할 수 있는 테스트**를 함께 추가.
3. 테스트가 통과하기 전까지 해당 작업을 "완료"로 간주하지 않는다.

도메인마다 테스트를 실행하는 방식(Apps Script Run, 스크립트 실행 등)은 다를 수 있지만, "테스트 없이 완료 없음" 원칙 자체는 모든 도메인에 동일하게 적용된다.

## Backward Compatibility

파일명, 함수명, 함수 시그니처, 기존 산출물(시트/문서/출력 포맷 등)은 승인 없이 변경하지 않는다.

- 다른 도메인이나 외부 시스템이 현재 산출물의 이름/형식에 의존하고 있을 수 있음을 항상 전제한다.
- 구조적 변경이 필요하다고 판단되면, 먼저 변경 범위와 영향을 설명하고 승인을 받은 뒤 진행한다.

## 도메인 간 관계

이 원칙들은 상위 원칙이며, 각 도메인의 실무 세부 규칙(네이밍 컨벤션, 파이프라인 구조 등)은 해당 도메인 문서를 따른다. 도메인별 상세 규칙과 라우팅은 [[domain-routing]], 공통 용어는 [[glossary]] 참고.
